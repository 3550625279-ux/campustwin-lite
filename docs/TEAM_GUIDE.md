## 三个模块的工作范围与交接

### A：校园环境与公共集成

维护 `include/campustwin/environment.hpp`、`accounts.hpp`、`src/environment/`、`src/simulation/`、`app/`、`examples/demo_a.cpp`、场景数据与对应测试；构建和 CI 变更需要说明对其他模块的影响。

| 能力 | 当前交付 | 核对重点 |
| --- | --- | --- |
| 场景读写与编辑 | 地点、道路、设施、窗口餐品、座位池配置；加载、校验、保存和重载 | 重复 ID、悬空引用、非法值、失败不替换有效场景 |
| 路线 | 无向加权图、Dijkstra 最短距离与实际路径 | 同点、不可达、多路线；道路修改后重新查询 |
| 公共集成 | `SimulationRunner`、CLI、统一 CMake 工程 | 只安排时钟和事件，不复制学生决策或排队算法 |
| 本地账号 | `demo_a` 注册/登录及受登录保护的管理操作 | 与统一仿真 CLI 分开，统一账号菜单尚未实现 |

交给其他模块：只读 `CampusScenario` 和 `IRouteProvider`。删除被道路或设施引用的地点应明确拒绝；学生引用在运行初始化时校验。不要默默删除下游配置来掩盖错误。

难点是场景一致性、图算法和公共集成工作量；调度暴露的问题应交给相应状态所有者处理，不能把所有业务修复都归给 A。

### B：学生、决策、日程与移动

维护 `include/campustwin/students.hpp`、`src/students/`、`examples/demo_b.cpp`、学生/日程输入及对应测试。

| 能力 | 当前交付 | 核对重点 |
| --- | --- | --- |
| 输入与运行状态 | `StudentSpec` 与私有运行状态分离；学生和日程 CSV 校验 | ID、速度、活动顺序、地点类型及午餐唯一性 |
| 出行与选择 | 路线查询、向上取整的移动时间、`fixed/nearest/fastest`、餐品过滤 | 冻结决策视图、不可达/不可服务候选、行顺序无关 |
| 事件驱动 | 到达、窗口开始/完成、座位请求/入座 | 请求唯一；错事件拒绝；收到反馈才改变相应状态 |
| 有序日程 | 上课、午餐、学习、休息；等座与活动状态；延迟传播 | 不抢跑、不跳过排队；仅最后一项完成才 `Finished` |
| 可观察结果 | 学生快照、候选决策、每项活动的实际时间与路径 | 未完成时刻留空，不能假定仿真截止前全部结束 |

只依赖 `IRouteProvider` 和只读 `IFacilityAdvisor`，通过调度层向 C 交付 `StudentArrival`、`SeatRequest`。B 维护个人行为，不维护窗口队列或擅自授予座位。难点是时间、状态和多事件对齐。

### C：服务资源、统计与输出

维护 `include/campustwin/resources.hpp`、`seats.hpp`、`reporting.hpp`、`src/resources/`、`src/reporting/`、`examples/demo_c.cpp`、资源测试和手算参考。

| 能力 | 当前交付 | 核对重点 |
| --- | --- | --- |
| 窗口 | 食堂公共队列、多个异质窗口、餐品匹配 | 按队列优先匹配，增广路径保留早到者并尽量填满兼容空闲窗口 |
| 服务事件与预测 | 开始/完成事件、只读冻结快照与无新增到达的耗时预测 | 不重复请求、不重复完成；明确预测假设 |
| 座位 | 按地点 FIFO，释放、分配与容量约束 | 同分钟释放复用；不能双重等待或占座 |
| 指标 | 窗口/座位等待、忙碌时间、队列峰值及利用率 | 占用区间 `[开始,结束)`，区分取餐完成与活动完成 |
| 结果记录 | 基础五份 CSV，日程/有限座位模式八份 | 格式稳定、拒绝覆盖、提前截止与重复运行可核对 |

C 发出 `ServiceStarted`、`ServiceCompleted`、`SeatGranted`；B 收到后自行改变学生状态。C 不选择学生目的地、不修改学生位置，不把等座时间算作占用取餐窗口。

## 公共文件与跨模块变更

| 变更范围 | 主维护与交接方式 |
| --- | --- |
| `contracts.hpp`、CSV 列、ID/时间单位、事件顺序、统计定义 | 提出影响说明，三人确认语义后在同一变更中迁移调用方与测试 |
| 场景/学生/服务输入 | A/B/C 分别维护对应部分，共同核对引用关系 |
| 根 CMake、CI、调度器 | A 组织；涉及其他模块时共同验证 |
| 记录器与报告数据 | C 维护统计口径，B 核对学生状态，A 核对路线与场景 |
| 联调与回归 | 状态属于哪个模块，问题由其维护人定位；共同保留可复现实验 |

只有调度器推进时间。公共事件是值对象；模块不互相访问私有容器，不复制第二套 `StudentId`、`SimTime` 或事件定义。实现内部的数据结构可以自行调整，前提是对外契约保持一致。

## 新成员开工

1. 从最新 `main` 获取源码，按 [README](../README.md) 构建、运行 CTest，再生成一次完整实验报告。
2. 阅读 [代码导览](00_REPOSITORY_GUIDE.md)、自己模块声明和 `contracts.hpp`，用一个真实学生追踪一次跨模块调用。
3. 查看模块测试和独立演示，选择一个当前尚未解决、可以单独验收的问题。下面的历史任务不是待认领清单。
4. 确认 A/B/C 与实际账号对应关系。仓库需有写入权限才能直接 push；没有时可 fork 后提 PR。
5. 建短期功能分支，记录输入、行为变化、验证和剩余限制。

独立演示入口：

```bash
./build/demo_a --scenario data/scenarios/mvp
./build/demo_b --students data/students/mvp.csv --student S001 --wait 3 --duration 20
./build/demo_c --facilities data/fixtures/resource_facilities.csv --arrivals data/fixtures/resource_arrivals.csv --duration 6
```

Windows 替换为实际生成的 `.exe` 路径。`demo_b` 使用路线与服务事件替身，不代表真实共享队列；集成仿真必须运行 `campustwin`。

## Git 与 PR 流程

每个可交付变更新建分支，不维持长期不合并的个人大分支。以下示例从已克隆、工作区干净的仓库开始：

```bash
git switch main
git pull --ff-only origin main
git switch -c feat/student-activity-update
```

完成修改后，构建并执行与变更相符的检查，明确选择要提交的文件：

```bash
cmake --build build --config Debug
ctest --test-dir build -C Debug --output-on-failure
git status
git add src/students/students.cpp include/campustwin/students.hpp
git commit -m "feat(students): update activity handling"
git push -u origin feat/student-activity-update
```

上面的 `git add` 只是示例；变更对应的测试、数据和文档也应逐项纳入。纯文档修改检查链接、命令和实际行为即可，不必为了文档新增业务测试。

提 PR 到 `main`，说明具体触发场景、前后行为、验证命令与结果、接口影响及尚未完成内容。正常团队流程由另一位成员审阅；公共协议变更让三人都知悉。合并后从最新 `main` 开始下一项工作。

需要同步功能分支时，先妥善提交本地修改，再运行：

```bash
git fetch origin
git merge origin/main
```

冲突逐文件解决，保留双方有效改动，重新验证后提交。不要用整份旧文件覆盖队友修改，不向 `main` 强推。

### 合并检查

- 统一工程可构建，功能有必要的独立或集成证据；绿色 CI 不能替代功能范围核对。
- 新增 `.cpp` 纳入对应 CMake 目标；业务库不含 `main`，独立入口留在 `examples/`。
- 每个 `.cpp` 自行包含标准头文件；不使用 `bits/stdc++.h`，公共头文件不放 `using namespace std;`，不写死个人电脑路径。
- 公共字段、事件与输出文档保持一致，没有用占位或预置结果假装完成。
- 不提交 `build/`、`outputs/`、个人 IDE 文件和真实账号数据。

建议管理员配置 PR 审阅和 Linux/Windows 构建要求、限制强推；本文不声明当前已启用分支保护，也不会自动变更仓库权限或邀请成员。

## 验收与开发记录

个人模块完成需要真实输入、独立演示/测试和可解释的输出；集成完成还需要真实模块连接、跨模块状态一致和端到端结果验证。

原 MVP 手算依据：20 人、两个窗口，总取餐等待 170 人·分钟、平均 8.5、最大阶段末队列 18；最后两人第 29 分钟结束返程。原检查器只对该固定输入有效。当前多活动、异质窗口和座位以 [升级验收](16_ACTIVITY_SCHEDULES.md#三阶段完成度与验证) 为准。

周记使用 [模板](weekly/TEMPLATE.md)，按实际课程周存入 `docs/weekly/week_NN_A.md` 等。记录提交/PR、输入、实际输出、问题根因与修复、下周一个明确交付物。不补写不存在的确认、测试或开发经历。

以下来自原始团队讨论对课程要求的转述，仓库没有老师要求原件；需要团队对照原文确认，不是“已全部满足”声明。
