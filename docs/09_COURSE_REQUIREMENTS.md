# 课程要求与设计落点

依据是团队提供的原始分工 v0.1 对课程要求的转述，本仓库没有老师要求的原件；提交前以老师原文为准。以下表格是核查清单，不是“已满足”声明。

| 要求 | 设计落点 | 应保留的证据 | 初始状态 |
| --- | --- | --- | --- |
| 三个独立子系统、最终统一程序 | A/B/C 库、三个 demo、一个 app | 独立运行和集成演示 | 只有骨架 |
| 类、封装、多文件 | 具体模块类与私有状态，hpp/cpp 分离 | 类图/代码说明 | 公共类声明就绪，业务待实现 |
| 继承、多态、类层次 | 接口→实现，Runner 经接口调用 | 运行时调用、析构、业务差异说明 | 接口就绪，需核对老师层次要求 |
| 文件数据处理 | 场景/学生输入、结果输出 | 重载一致、错误输入与写失败测试 | 格式已定，代码待实现 |
| 用户账号密码与权限 | 核心闭环后由 A 负责 | 注册/登录/权限与持久化演示 | 下一迭代，最终提交必需 |
| 每周周记 | `docs/weekly/` | 真实提交与问题记录 | 模板已备 |
| 正确性、测试 | 独立边界测试 + 集成基准 | 手算/自动检查/实验输出 | 样例校验与验收工具已备 |
| 答辩、报告 | 每人讲自己的状态和接口 | 实际代码、运行证据 | 后续准备 |
| 不把 AI 完整成品直接交作业 | 人工实现并理解核心算法 | 说明辅助范围、独立解释 | 本次只给设计与占位工程 |

账号具体实现方案与许可方式在课程补齐阶段讨论；公开仓库只放虚构测试账号配置，真实凭据或本机用户数据不进入版本库。

MVP 的范围裁剪用于先跑通系统，不能从课程最终验收中删除硬性要求。三人应在开始时核对一次原件，避免最后一周才发现理解有偏差。
