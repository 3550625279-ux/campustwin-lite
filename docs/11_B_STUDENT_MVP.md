# B 学生模块：实现、运行与交接

B 已实现 `read_student_specs` 与 `StudentEngine` 的全部现有接口。公共 `contracts.hpp` 不变；A、C、记录器和真实调度器仍待各自实现，整个项目尚不能作为完整仿真器验收。

## 1. 先运行一个学生

在仓库根目录执行：

```bash
cmake -S . -B build
cmake --build build --config Debug
ctest --test-dir build -C Debug --output-on-failure
./build/demo_b --students data/students/mvp.csv --student S001 --wait 3 --duration 20
```

Windows 多配置生成器使用 `build/Debug/demo_b.exe`。`--help` 查看参数；`--students` 默认样例 CSV，`--student` 默认 S001，`--wait` 默认 0，`--duration` 默认 20、至少 1。

演示会先解析整个文件，再选一名学生运行。A 被固定的路线提供者替代，C 被单学生的服务脚本替代；脚本仅在到达后等待指定分钟再通知开始，2 分钟后通知完成。输出开头会明确标出这一边界。它没有实现队列、场景文件解析或四份 CSV。

`--wait 3` 时 S001 的阶段末状态：

| 时刻 | 状态 | 触发因素 |
| --- | --- | --- |
| 0、1 | Moving | 120 米 / 60 米每分钟，行走 2 分钟 |
| 2、3、4 | Queued | 已到达，脚本尚未通知服务开始 |
| 5、6 | InService | 收到开始事件 |
| 7…11 | Eating | 收到完成事件，吃饭 5 分钟 |
| 12、13 | Moving | 就餐到期，开始返回 |
| 14 起 | Finished | 返回宿舍，后续快照仍保留此人 |

最终输出 `SUMMARY students=1 arrivals=1 finished=1`。将等待改为 0，完成返回应提前到 t=11；将 duration 改为 3，学生保留 Queued，`finished=0` 是正常截止结果。

## 2. 按实现顺序阅读代码

| 阶段 | 实现位置 | 解决的问题 |
| --- | --- | --- |
| 读取配置 | `read_student_specs` 及解析辅助函数 | 严格表头和 7 列；CRLF/LF、空行；拒绝重复 ID、错误数字和非法字段，报文件与物理行号 |
| 初始化 | `reset` | 校验地点/设施引用；创建运行状态；失败不破坏原运行 |
| 移动到达 | `tick` 的 AtLocation / Moving 分支 | 到出发时刻查路线，计算 ceil 耗时；食堂到达产生一次唯一请求 |
| 服务反馈 | 两个 `on_service_*` | 校验身份、窗口、时刻和当前状态，再改变状态 |
| 就餐返回 | `tick` 的 Eating / Moving 分支 | 以真实完成通知为起点计算就餐；返程不再发午餐请求 |
| 只读输出 | `snapshots` | 输出排序后的值对象，Moving 没有地点，其余状态没有移动字段 |

配置 `StudentSpec` 描述“这个学生应当怎样行动”；私有 `StudentRuntime` 描述“现在执行到哪里”。其中 `returning` 区分同为 Moving 的去程和返程，`service` 保存开始事件以校验完成通知，`eating_until` 决定何时返程。

设施 ID 与地点 ID 分开：`F_CANTEEN` 先由场景映射到 `L_CANTEEN`，路线查询使用地点 ID。B 按最短路线总距离计算耗时，不逐道路插值，也不重复实现 A 的最短路算法。

## 3. 与 A、C 接口对齐

Runner 先调用 `reset`。每分钟从 0 连续推进，不重复、不跳号：

1. C 完成阶段产生 `ServiceCompleted`，逐条通知 B。
2. 调用 B `tick(t, routes)`；得到本分钟的 `StudentArrival`。
3. 将到达交给 C 入队；C 开始阶段产生 `ServiceStarted`，逐条通知 B。
4. 读取 `snapshots(t)`，交给真实记录器。

因此完成通知属于下一个尚未 tick 的分钟，开始通知属于当前刚 tick 的分钟。收到下一分钟的完成通知后，上一分钟的快照已不再可读；应先执行新的 tick。

缺少开始事件时学生保持 Queued；缺少完成事件时保持 InService。固定服务时长的完成事件必须满足 `completed.at = started.at + service_minutes`，迟到或错时刻的事件报错，B 不自行猜测或补发事件。延迟服务的实验通过推迟开始事件、再按实际配置完成来表达。

`reset` 保存自有数据，不保留指向 A/C 容器的指针。学生和设施状态仍分别归 B/C 所有；B 不检查所有学生是否竞争同一窗口，这属于 C 的资源互斥责任。

## 4. 独立验证到哪里

CTest 包含 3 项：样例数据合同、学生引擎行为、B 独立演示。行为测试包含 21 组用例，使用普通 C++17，无额外测试框架。

重点验证：

- 121 米、60 米/分钟向上取整为 3 分钟；任意正距离至少 1 分钟。
- 非零出发时间、不可达、非有限距离、数值和时间加法溢出。
- 唯一请求、两种外部反馈、错误/重复反馈拒绝、同分钟多个完成通知。
- 连续 tick、阶段末快照、读快照不改变状态，返回的是独立值对象。
- reset 清理旧运行；非法 reset 和路由失败不提交半份更新。
- 20 人在 t=2/t=3 各到 10 人；使用外部手算服务事件后，全部 2420 条学生状态符合预期，t=29 全部返回。

最后一项是 B 对固定外部事件的验证。测试脚本只放在 `tests/`，没有进入学生引擎。真实 C 排队、A 路线、四份输出和 `check_mvp_outputs.py` 仍需要联合验收。

## 5. 实现取舍与交付边界

初始化时按 ID 排序，并建哈希索引。每分钟遍历学生；反馈事件平均常数时间定位学生，快照按已有顺序输出。为了让一次 tick 失败后可重试，先在学生运行数据副本上计算，成功后交换，额外临时内存为 O(N)；当前 N=20，优先保持失败处理清晰。

本阶段没有实现随机行为、复杂日程冲突、图形界面、数据库和全项目账号功能。它们不进入 B 的午餐链实现。

本次代码与测试由 AI 辅助完成。负责成员需要自行复跑、逐段审阅和解释，按课程要求记录辅助范围；不能把本分支描述为未经辅助的独立实现。
