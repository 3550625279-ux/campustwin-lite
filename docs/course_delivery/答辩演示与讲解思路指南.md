> **适用场景**：华南理工大学计算机科学与工程学院《面向对象程序设计》课设答辩（A1-101，沃焱老师 & 助教检查）

## 一、整体答辩节奏设计（黄金“三段式”）

根据答辩通知要求，现场包含 **找老师 PPT 答辩 + 找对应助教演示并测试程序** 两个环节。推荐采用以下黄金时间分配：

1. **痛点切入与系统定位（约 45 秒）**：用一句话和真实场景抓住老师——“上午下课去哪家食堂？窗口排多久、有没有座位，会怎样连锁导致下午上课和图书馆自习迟到？我们用纯标准库 C++17 构建了分钟级校园数字孪生仿真器 CampusTwin Lite。”
2. **面向对象架构、四大技术亮点与三人分工（约 3 分钟）**：对应答辩要求 **(a)** —— 讲清 `contracts.hpp` 抽象接口类体系、多态 `IRunWriter`、单分钟八阶段时序与守恒断言，明确点出 **A / B / C 每位同学负责的类和文件**。
3. **现场 TUI 演示 + 定量实验发现 + 差距反思（约 2.5 分钟）**：对应答辩要求 **(b)** —— 演示命令行动态看板与四组对照实验（抛出“图书馆座位翻倍提前 30 分钟结束，而食堂座位翻倍几乎无效”的反直觉结论），最后主动、诚实地剖析 **当前系统与预期目标的差距、存在的主要问题与下一步工作**（老师极看重工程诚实度！）。

## 二、PPT 逐模块讲解思路与口播话术（紧扣答辩通知 a & b）

### 第 1 部分：课题背景与要解决的核心问题
- **讲解主线**：校园资源（道路、异质食堂窗口、食堂/图书馆座位）与学生全天日程存在强时序耦合，单点排队会沿时间轴向后传播。
- **口播要点**：
  > “各位老师好，我们组展示的课题是 **CampusTwin Lite 校园出行、活动与服务数字孪生仿真系统**。在真实校园中，学生并不是只去吃一顿饭就结束，而是串联着‘早课 → 午餐 → 午后课 → 图书馆自习 → 研讨 → 归寝’的完整日程。我们希望用一套零外部依赖的 C++17 离散事件仿真引擎，定量回答：改一条路、加一个窗口、换一种选食堂策略、或者给图书馆扩座，到底会怎样改变全校学生的排队与迟到？”

### 第 2 部分：面向对象类体系与程序结构设计（答辩要求 a 核心！）
- **讲解主线**：重点展示 **为什么这样设计继承与多态**（避免为了凑语法写无意义的 `Cat : Animal` 继承，展示真正的软件工程接口多态！）。
- **必讲的 4 条核心多态/封装链**：
  1. **最小权限接口继承链**：`IRouteProvider` 只暴露 `find_route()` 给学生模块，派生出 `ICampusEnvironment` 再由 `CampusEnvironment` 具体实现——保证学生引擎绝不可能越权篡改地图配置。
  2. **多态输出与前端解耦链（最大 OOP 亮点！）**：抽象基类 `IRunWriter` 定义了仿真输出协议。模块 C 实现了写磁盘的 `CsvRunWriter`；为了在不改动一行核心调度代码的前提下做出命令行可视化前端，我们基于**开闭原则（OCP）**和**组合模式（Composite Pattern）**新增了 `InMemoryRunObserver`（捕获逐分钟内存态势帧）和 `CompositeRunWriter`（同时写内存与 CSV）。`SimulationRunner` 只持有 `IRunWriter&` 基类引用即可多态驱动！
  3. **静态规格与私有运行态分离**：`StudentEngine` 将公开只读输入 `StudentSpec` 与私有状态机 `StudentRuntime` 严格分离，任何外部模块只能通过值对象事件通知学生，不能直接改学生坐标。
  4. **单分钟八阶段确定性时序与双向守恒断言**：展示 `SimulationRunner` 的 8 个阶段（冻结 `t-1` 快照 → 完成窗口 → 释放座位 → 学生推进 → 窗口入队分配 → 座位入队分配 → **双向守恒校验** → 多态输出）。

### 第 3 部分：四大硬核算法与工程技术亮点
1. **`t-1` 冻结快照（`FrozenAdvisor`）消除遍历顺序偏见**：同一分钟出发的 60 名学生观察到的是完全一致的上一分钟队列快照，再配合按学号字典序排序，确保 CSV 行顺序任意打乱后仿真结果**字节级 100% 一致**。
2. **异质餐品窗口的二分图 BFS 增广路径匹配（`assign_windows`）**：支持专用窗与 `*` 通配窗混合。当后到学生需要特定餐品时，增广路径可把本分钟刚匹配的早到学生平移到另一兼容空闲窗，既严格保护 FIFO 早到者权益，又最大化消灭窗口空置。
3. **零第三方依赖的密码学账号与三级 RBAC 权限（`AccountStore` + `RoleStore`）**：手写标准 FIPS 180-4 SHA-256、HMAC 与 20 万次迭代 PBKDF2（通过 NIST/RFC 标准向量测试），具备常量时间比对与临时文件原子落盘，在 TUI 中实现 `Guest / Student / Admin` 三级权限门禁。
4. **原生 C++17 交互式终端工作台（`ConsoleWorkbench`）**：毫秒级内存仿真、逐分钟进度条动画回放、拥堵峰值一键定位、单人甘特时间轴色带与四组内存控制变量实验一键对比。

### 第 4 部分：小组成员分工说明（务必清晰到文件与类！）
- **模块 A 负责人**：负责 `CampusEnvironment`、`AccountStore`、`SimulationRunner`（`src/environment/`、`src/simulation/`），完成无向图 Dijkstra 最短路、5 类场景 CSV 强异常安全加载保存、PBKDF2 本地账号安全及跨模块守恒检查。
- **模块 B 负责人（Edward）**：负责 `StudentEngine`（`src/students/`），完成 7/8/9 列学生与乱序日程 CSV 校验、`fixed/nearest/fastest` 三策略评估记录、8 状态有限自动机以及全天日程提前出发与迟到延迟传播。
- **模块 C 负责人**：负责 `FacilityEngine`、`SeatEngine`、`CsvRunWriter`（`src/resources/`、`src/reporting/`、`tools/`），完成异质窗口增广匹配、冻结等待预测、有限座位同分钟释放复用、防覆盖 CSV 记录器及离线 HTML 实验脚本。
- **公共联调与 TUI 前端**：三人共同冻结 `contracts.hpp` 契约，通过 `ConsoleWorkbench`（`src/tui/`）将账号权限、实时仿真看板、单人透视、对照实验与在线地图编辑整合为统一交互入口，并完成 20 项 CTest 自动验收。

### 第 5 部分：已完成功能、实验结论与“预期差距/存在问题/下一步工作”（答辩要求 b 必考！）
- **已完成核心功能**：
  - 完整交付原始 20 人 MVP 基准 + 三个升级阶段（动态选食堂、异质餐品窗口、36 人 216 项多活动日程与 6 处有限座位池）+ C++17 交互式 TUI 工作台 + 离线多阶段 HTML 报告 + 20 项 CTest 100% 通过。
  - **关键定量发现**：在全天日程场景中，**食堂座位翻倍几乎不改变全员完成时间（124 分钟），而图书馆座位翻倍使总等座下降 59.7%（885→357 分）、全员完成提前 30 分钟（94 分钟）**；封闭 3 条道路虽因绕行错峰使等座微降，但总里程增至 34800 米、课程迟到恶化至 1055 分钟。
- **与预期目标的差距 & 当前存在的主要问题（主动坦诚展示深度思考！）**：
  1. **动态决策前瞻视野有限**：当前 `fastest` 策略仅根据 `t-1` 窗口状态估算到“窗口取餐结束”的耗时，**未将食堂等座时间、未来在途竞争者以及下午上课的硬截止时间纳入效用函数**，导致部分食堂虽然取餐快但等座久。
  2. **路网移动为离散整段推进**：目前一段移动按 `ceil(距离 / 步速)` 一次性跨越起点至终点，**未模拟道路通行容量拥堵、红绿灯、自行车/校车多交通工具**，也不支持学生在步行途中收到拥堵通知后动态改道。
  3. **日程规则刚性**：当前要求每人固定单日一次午餐，迟到后仍刚性执行完整时长，尚不支持**超时主动退选/跳过自习、图书馆提前预约选座或跨日多餐循环**。
  4. **可视化形态边界**：命令行 TUI 与离线 HTML 拓扑图侧重逻辑状态与统计精确性，尚无基于真实校园经纬度的 2D/3D 连续人物动画。
- **下一步主要工作**：
  1. 升级 `IFacilityAdvisor` 联合 `ISeatEngine` 快照，实现**“路途 + 取餐等待 + 预计等座 + 课程迟到惩罚”多目标决策策略**；
  2. 在 `Road` 模型中引入容量密度函数与校车/单车边权，支持途中重路由；
  3. 扩展 WebSocket 实时图形化沙盘前端，对接真实华工五山/大学城校区路网数据开展校准实验。

## 四、老师与助教高频提问应对宝典（Q&A Cheat Sheet）

1. **问：你们系统里的面向对象“继承和多态”具体体现在哪里？有没有为了凑要求硬写继承？**
   - **答**：我们严格遵循工程契约设计，没有写无意义的业务实体继承（比如硬把教学楼和食堂写成派生类而没有任何虚函数行为差异），而是把继承与多态用在真正的模块解耦边界上：
     - 一是 `IRouteProvider` → `ICampusEnvironment` → `CampusEnvironment` 的接口收窄继承，让 `StudentEngine` 只拿最小路由查询权限；
     - 二是 `SimulationRunner` 完全面向 `IStudentEngine`、`IFacilityEngine`、`ISeatEngine`、`IRunWriter` 四个纯虚接口编程，使单元测试能注入 Mock 替身独立测试；
     - 三是 `IRunWriter` 多态派生出 `CsvRunWriter`、`InMemoryRunObserver` 与组合模式的 `CompositeRunWriter`，让我们本次新增命令行 TUI 时对核心调度器做到了**零代码修改**（严格符合开闭原则）。
2. **问：同一分钟如果有多个学生同时出发选食堂或者同时到达排队，结果会不会跟 CSV 文件里谁写在前面有关？**
   - **答**：完全无关！我们做了两重确定性保证：第一，`StudentEngine::reset()` 加载后立即按学号字典序排序，`FacilityEngine::enqueue()` 和 `SeatEngine::enqueue()` 对同分钟新请求也按 `(student_id, request_id)` 排序；第二，选食堂读取的是分钟开始前通过 `decision_snapshot()` 冻结的 `t-1` 快照，先遍历到的学生不会污染同分钟后遍历学生的观察视图。我们的 `test_schedules.py` 专门把输入 CSV 完全倒序重跑，验证输出的 8 份 CSV 字节级 100% 相同。
3. **问：异质窗口匹配如果队首学生的餐品当前空闲窗口做不了，后面的学生会被卡死吗？**
   - **答**：不会卡死，也不会乱插队。`assign_windows()` 按队列先后顺序对每位等待者做二分图 BFS 增广路径搜索：如果队首需要的现炒窗口正忙，但米饭窗空着，队首保留在队列最前等待，后面买米饭的学生可以正常进入空闲米饭窗；而且如果前一个人既能去通用窗又能去专用窗，增广路径会自动把他平移到通用窗，把专用窗腾给后面只能去专用窗的同学。
4. **问：如果助教现场故意把 CSV 某一行改错（比如把步速改成 0，或者删掉一条通往食堂的唯一道路），程序会崩溃或者覆盖旧结果吗？**
   - **答**：绝不会。第一，`CsvRunWriter::begin()` 发现目标目录已有同名 CSV 会直接拒绝运行，保护历史实验数据；第二，所有输入解析都使用 `std::from_chars` 与显式范围检查，步速为 0、负数、BOM、列数不对、悬空地点 ID 都会在开始前抛出定位到具体文件行号的 `ValidationError`；第三，`CampusEnvironment` 与各引擎的 `reset/replace` 全部采用**先构造局部副本再 `std::swap`** 的强异常安全模式，失败后内存原状态完整保留。
5. **问：开发过程中如果使用了 AI 辅助，你们是如何把控正确性的？**
   - **答**：（按 `TEAM_GUIDE.md` 诚实规范作答）我们在文档整理、脚手架与交互前端构建中合理借助了 AI 辅助，但核心接口契约（`contracts.hpp`）、单分钟八阶段时序定义、20 人 MVP 手算黄金基准（170 人·分钟等待）以及每分钟双向人数守恒断言（`check_snapshots` / `check_seats`）均经过人工推导与 20 项 CTest 交叉核验，确保每一行逻辑可解释、可手算复核。
