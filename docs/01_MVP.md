# 第一阶段：MVP 产品定义

## 要证明的事情

这不是提前填写人数表再播放。学生什么时候到达取决于道路和速度；什么时候取到餐取决于排队和窗口；什么时候离开食堂取决于真实服务完成时刻。修改道路距离或窗口数，应当改变后续轨迹与统计。

## 固定场景

| 输入 | 第一轮基准 |
| --- | --- |
| 地点 | 教学楼 T1/T2、食堂、宿舍、图书馆，各有稳定 ID |
| 人群 | S001–S010 从 T1 出发，S011–S020 从 T2 出发 |
| 时间 | 12:00 = t=0；模拟 t=0…120，单位分钟 |
| 路线 | T1→食堂 120 m；T2→食堂 180 m；食堂→宿舍 120 m |
| 学生 | 速度 60 m/min，t=0 下课，取餐后吃饭 5 min |
| 食堂 | 一个公共队列、2 个窗口、每次服务 2 min |
| 决策 | 按日程前往指定食堂，吃完返回指定宿舍 |

图书馆先用于证明场景能表示其他地点，不在第一轮行为链中分配座位。道路按无向图处理，距离取最短路径总长。完整配置在 `data/`。

## 最小用户流程

1. 用户加载场景和学生 CSV；程序检查 ID、参数及引用关系。
2. 用户启动一次仿真，统一调度器从 t=0 推进至 t=120。
3. 程序按状态机产生移动、到达、排队、取餐、就餐和返回。
4. 用户查看结束摘要，并打开四份 CSV：事件、学生快照、设施快照、设施汇总。
5. 用户修改窗口数或距离后重新运行到另一输出目录，进行对照。

第一阶段先完成 CLI 加载与运行；A 的场景编辑 API 与独立演示需能新增、修改、删除地点/道路并保存。统一交互菜单可在核心闭环后接入，不阻塞 B/C 开发。

## 必做与延期

| 第一阶段必做 | 后续迭代 |
| --- | --- |
| 场景校验、文件读写、路径查询 | 真实校园地图与校准 |
| 固定日程、移动、学生状态机 | 动态偏好、骑车、复杂活动冲突 |
| FIFO 队列、多个窗口、正确服务事件 | 多食堂、图书馆座位、体育馆 |
| 唯一时钟、确定顺序、可复现输出 | 随机行为与固定随机种子 |
| 独立演示、联合运行、指标导出 | 图形界面、数据库、联网 |

账号与权限在原分工中被记录为课程硬性要求，安排在核心 MVP 之后的下一迭代，**最终提交前仍必须完成**，不能以“MVP 不做”代替课程交付。

## 完成标准

下列项全部通过，才可以标记 MVP 完成：

- [x] A/B/C 各自独立运行，展示真实输入、处理过程和输出。
- [x] 联合程序通过样例 20 人的全部验收；不是使用预置结果替代仿真。
- [x] 固定样例每个学生在每个快照只占一个主要状态；在途学生不重复计入地点人数。
- [x] 联合程序每次快照检查队列、窗口和 B 的学生状态一致。
- [x] 修改窗口数或距离能产生对应的因果变化。
- [x] 两次使用相同输入运行，四份结果逐字节相同。
- [ ] 三位成员分别能解释自己维护的类、数据、算法和边界处理。

以上勾选依据本地自动化测试及固定样例验收，不能证明所有可能场景。成员是否理解代码仍须团队自行确认；课程最终交付也需要核对 [课程要求](09_COURSE_REQUIREMENTS.md)。
